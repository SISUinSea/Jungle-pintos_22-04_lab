Pintos Project 3: Virtual Memory TopDown 학습 문서

처음 Project 3을 볼 때 필요한 핵심 키워드만 먼저 예열하고, 그 다음 전체 구조에서 구현 단위로 내려갑니다. 목표는 코드를 바로 외우는 것이 아니라 "페이지 폴트가 났을 때 커널이 무엇을 판단하고 무엇을 복구하는가"를 잡는 것입니다.

0. 아주 짧은 예열: 핵심 용어

Project 3의 중심 문장은 하나입니다. 사용자 프로그램이 어떤 가상 주소에 접근했는데 아직 물리 메모리가 준비되지 않았다면, 커널이 그 접근을 해석해서 필요한 페이지를 준비한다.

가상 페이지와 프레임

page는 사용자 입장에서의 한 페이지입니다. 보통 사용자 가상 주소 va와 연결됩니다.

frame은 실제 물리 메모리 한 칸입니다. Pintos 코드에서는 커널이 만질 수 있는 주소 kva로 들고 있습니다.

SPT

supplemental_page_table은 "이 프로세스의 가상 페이지 설계도"입니다.

하드웨어 페이지 테이블인 pml4는 현재 매핑만 알지만, SPT는 아직 메모리에 없는 페이지도 기억해야 합니다.

Page Fault

CPU가 주소 접근에 실패하면 page_fault()가 호출됩니다.

Project 3에서는 무조건 죽이는 대신, vm_try_handle_fault()에서 복구 가능한 fault인지 판단합니다.

Lazy Loading

프로그램 실행 시 모든 바이트를 즉시 읽지 않습니다.

먼저 SPT에 "나중에 이 주소가 필요하면 파일의 이 위치에서 읽어라"라는 예약만 넣고, 실제 접근이 오면 로드합니다.

Anonymous Page

파일과 직접 연결되지 않은 페이지입니다. 대표적으로 스택, 힙 비슷한 일반 메모리, 0으로 채우는 페이지가 여기에 가깝습니다.

File-backed Page와 mmap

파일 내용을 가상 메모리처럼 보이게 하는 페이지입니다. mmap으로 만든 매핑은 파일의 특정 구간과 연결됩니다.

Swap In/Out

메모리가 부족하면 덜 급한 페이지를 디스크의 swap 영역으로 내보냅니다. 다시 필요하면 swap에서 읽어옵니다.

Dirty와 Accessed

dirty는 페이지가 수정되었는지, accessed는 최근 접근되었는지 보는 힌트입니다.

파일에 다시 써야 하는지, 어떤 프레임을 쫓아낼지 판단할 때 중요합니다.

1. Top Level: Project 3은 무엇을 만드는가

Project 2에서는 프로그램을 실행할 때 필요한 페이지를 거의 즉시 물리 메모리에 올렸습니다. Project 3에서는 이 방식을 더 운영체제답게 바꿉니다. "필요할 때 올리고, 부족하면 내보내고, 다시 필요하면 되살리는" 구조를 만듭니다.

1. 예약load_segment가 실제 로드 대신 SPT에 페이지 정보를 넣습니다.
2. 접근사용자 코드가 아직 매핑되지 않은 주소를 읽거나 씁니다.
3. 폴트page_fault가 vm_try_handle_fault로 넘깁니다.
4. Claim프레임을 받고 pml4에 매핑한 뒤 내용을 채웁니다.
5. 교체메모리가 부족하면 victim을 골라 swap out 합니다.
읽는 관점: Project 3 코드는 "할당 함수"보다 "fault 복구 파이프라인"으로 보는 편이 쉽습니다. 주소 접근 실패가 들어오고, SPT를 조회하고, 프레임을 마련하고, 타입별 swap_in이 데이터를 채웁니다.

2. 큰 구조: 두 개의 테이블을 같이 이해하기

구조 역할 언제 중요해지는가
pml4 하드웨어가 실제 주소 변환에 사용하는 페이지 테이블입니다. 이미 물리 프레임에 올라온 페이지를 CPU가 접근할 때 필요합니다.
supplemental_page_table 커널이 추가로 들고 있는 페이지 메타데이터입니다. 아직 로드되지 않았거나, swap에 있거나, 파일에서 읽어야 하는 페이지를 찾을 때 필요합니다.
frame table 현재 물리 메모리에 올라온 프레임 목록입니다. 메모리가 부족해서 어떤 프레임을 내보낼지 고를 때 필요합니다.

핵심은 pml4만으로는 lazy loading을 구현할 수 없다는 점입니다. 아직 물리 메모리에 없는 페이지는 pml4에 매핑이 없으므로, 커널이 SPT에서 "이 주소는 정상적인 예약 페이지인가"를 따로 찾아야 합니다.

3. 구현 단위 1: SPT부터 세운다

가장 먼저 각 프로세스가 자기 가상 페이지 목록을 들고 있게 해야 합니다. Pintos 템플릿의 struct supplemental_page_table은 비어 있으므로, 보통 해시 테이블을 넣어 va로 struct page를 찾게 만듭니다.

  • supplemental_page_table_init: SPT 자료구조 초기화
  • spt_find_page: 주소를 page 단위로 내림 정렬한 뒤 해당 struct page 찾기
  • spt_insert_page: 중복 주소가 없을 때 SPT에 page 삽입
  • supplemental_page_table_copy: fork 때 부모 SPT를 자식에게 복사
  • supplemental_page_table_kill: 프로세스 종료 때 모든 페이지 자원 정리
SPT의 key는 "정확한 fault 주소"가 아니라 page base 주소여야 합니다. 예를 들어 0x8048123 접근은 pg_round_down(0x8048123)로 같은 페이지를 찾아야 합니다.

4. 구현 단위 2: Page와 Operations를 이해한다

struct page는 Project 3의 중심 객체입니다. 페이지마다 타입이 다르기 때문에, Pintos는 C에서 간단한 다형성처럼 struct page_operations 함수 포인터를 사용합니다. 

struct page_operations {
  bool (*swap_in) (struct page *, void *);
  bool (*swap_out) (struct page *);
  void (*destroy) (struct page *);
  enum vm_type type;
};

그래서 공통 코드에서는 swap_in(page, kva)만 호출해도 됩니다. 실제로는 페이지 타입에 따라 anon_swap_in, file_backed_swap_in, uninit_initialize 중 하나가 호출됩니다.

처음에는 모든 lazy page가 VM_UNINIT으로 태어납니다. 첫 page fault가 발생해서 swap_in이 호출되면, 그때 진짜 타입인 VM_ANON 또는 VM_FILE로 초기화됩니다.

5. 구현 단위 3: Lazy Loading 흐름

실행 파일 로드는 Project 3에서 가장 먼저 감각을 잡아야 하는 부분입니다. 기존에는 load_segment가 파일을 바로 읽어 물리 페이지에 채웠다면, 이제는 "나중에 읽을 정보"를 aux에 담아 예약합니다.

  1. load_segment가 페이지별 read_bytes, zero_bytes, ofs, file 정보를 만든다.
  2. vm_alloc_page_with_initializer로 VM_ANON 또는 필요한 타입의 uninit page를 SPT에 넣는다.
  3. 사용자 프로그램이 그 주소에 처음 접근한다.
  4. vm_try_handle_fault가 SPT에서 page를 찾고 vm_do_claim_page를 호출한다.
  5. uninit_initialize가 lazy_load_segment를 호출해 파일 내용을 실제 프레임에 채운다.
여기서 aux는 미래의 나에게 남기는 쪽지입니다. "이 페이지를 실제로 만들 때 어떤 파일의 어느 offset에서 몇 바이트를 읽고, 나머지는 몇 바이트를 0으로 채울지"를 담습니다.

6. 구현 단위 4: Page Fault 처리

userprog/exception.c의 page_fault()는 fault 주소를 rcr2()로 얻고, 접근 종류를 not_present, write, user로 해석합니다. Project 3의 진짜 판단은 vm_try_handle_fault()에서 합니다.

상황 처리 방향
SPT에 있는 lazy page 접근 vm_do_claim_page로 프레임을 붙이고 swap_in 합니다.
스택 근처 접근 스택 증가로 인정할 수 있으면 vm_stack_growth로 새 anon page를 만듭니다.
쓰기 금지 페이지에 write 기본 과제에서는 대개 실패 처리입니다. COW extra를 한다면 별도 처리합니다.
커널 주소, NULL, 완전히 엉뚱한 주소 복구할 수 없는 fault이므로 프로세스를 종료해야 합니다.

7. 구현 단위 5: Frame 관리와 Eviction

vm_get_frame은 user pool에서 물리 페이지를 가져와 struct frame으로 감쌉니다. 프레임을 받으면 vm_do_claim_page가 page와 frame을 서로 연결하고, pml4_set_page로 실제 매핑을 만듭니다. 

page fault
  -> spt_find_page
  -> vm_claim_page
  -> vm_get_frame
  -> pml4_set_page
  -> swap_in(page, frame->kva)

메모리가 부족하면 vm_get_frame은 새 프레임을 못 받습니다. 이때 vm_evict_frame이 victim을 골라 swap_out하고, 비워진 프레임을 재사용해야 합니다.

프레임을 내보낼 때는 pml4 매핑도 끊어야 합니다. 그렇지 않으면 CPU는 이미 쫓겨난 물리 프레임을 여전히 유효하다고 믿을 수 있습니다.

8. 구현 단위 6: Anonymous Page와 Swap

Anonymous page는 원본 파일이 없습니다. 따라서 메모리에서 쫓겨날 때 보관할 곳이 필요하고, 그곳이 swap disk입니다.

  • vm_anon_init: swap disk를 찾고, swap slot 사용 여부를 관리할 자료구조를 초기화합니다.
  • anon_initializer: page의 operations를 anon_ops로 바꾸고 swap 관련 메타데이터를 초기화합니다.
  • anon_swap_out: 비어 있는 swap slot을 찾아 한 페이지를 섹터 단위로 기록합니다.
  • anon_swap_in: 저장된 swap slot에서 다시 읽고, 그 slot을 해제합니다.

swap slot은 미리 잡아두지 말고 실제로 쫓겨날 때 할당하는 방식이 자연스럽습니다. 다시 읽혀 들어온 slot은 즉시 비워야 다음 eviction에서 재사용할 수 있습니다.

9. 구현 단위 7: Stack Growth

Project 2의 스택은 처음 만든 한 페이지가 전부였습니다. Project 3에서는 사용자 프로그램이 스택을 더 쓰려고 할 때, 그 접근이 스택 증가로 보이면 새 anonymous page를 추가합니다.

  • fault 주소가 사용자 주소인지 확인합니다.
  • fault 주소가 현재 rsp 근처인지 확인합니다.
  • 최대 스택 크기 제한을 넘지 않는지 확인합니다.
  • 인정되면 pg_round_down(addr)에 VM_ANON 페이지를 만들고 claim합니다.
스택은 아래 방향으로 자랍니다. 주소가 작아지는 방향입니다. 그래서 "USER_STACK보다 아래에 있고, 현재 rsp에서 너무 멀지 않은 주소"인지 보는 감각이 중요합니다.

10. 구현 단위 8: mmap과 File-backed Page

mmap은 파일을 메모리처럼 보이게 합니다. 사용자가 addr부터 읽으면 사실은 파일의 offset부터 읽는 식입니다. 하지만 이것도 lazy하게 만들어야 하므로, 매핑 시점에는 file-backed page들을 SPT에 예약하고 실제 읽기는 fault 때 수행합니다.

  • mmap: syscall 인자 검증 후 do_mmap 호출
  • do_mmap: 파일 길이만큼 연속 가상 페이지를 예약
  • file_backed_swap_in: 파일에서 읽고 남는 부분은 0으로 채움
  • file_backed_swap_out: dirty page라면 파일에 다시 기록
  • munmap: 매핑 범위의 페이지를 정리하고 필요한 write-back 수행
mmap은 검증 조건이 많습니다. addr == NULL, 길이 0, 페이지 정렬 안 됨, 기존 SPT 영역과 겹침, fd가 stdin/stdout, offset 정렬 문제 같은 케이스를 초기에 막아야 합니다.

11. 추천 구현 순서

  1. SPT 자료구조와 spt_find_page, spt_insert_page를 먼저 완성합니다.
  2. vm_alloc_page_with_initializer와 uninit page 생성 흐름을 연결합니다.
  3. vm_get_frame, vm_claim_page, vm_do_claim_page를 구현해 claim 경로를 만듭니다.
  4. load_segment, lazy_load_segment, setup_stack을 lazy 방식으로 바꿉니다.
  5. vm_try_handle_fault에서 SPT 조회와 stack growth 판단을 연결합니다.
  6. 프로젝트 2 테스트와 lazy 관련 VM 테스트를 먼저 봅니다.
  7. frame table과 eviction을 추가합니다.
  8. anonymous swap in/out을 구현합니다.
  9. mmap, file-backed page, munmap write-back을 구현합니다.
  10. fork, process exit, SPT copy/kill 정리를 단단히 맞춥니다.

13. 처음 읽을 때의 mental model

Project 3을 한 번에 "가상 메모리 전체"로 보면 너무 큽니다. 대신 아래 질문 하나로 계속 돌아오면 됩니다.

이 주소는 어디서 온 페이지인가? 실행 파일 스택 mmap 파일 swap disk

답을 찾으면 다음 행동도 정해집니다. 실행 파일이면 lazy loader가 파일에서 읽고, 스택이면 anonymous page를 만들고, mmap이면 file-backed page로 읽고, 이미 쫓겨났던 페이지면 swap slot에서 되살립니다.
